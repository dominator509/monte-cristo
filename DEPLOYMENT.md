# DEPLOYMENT -- MONTE CRISTO

Auto-Deploy Authorization for this project is **no**. The run completes the entire ship gate
and stops at a proven, tagged, ship-ready artifact set. The final publish step is emitted as
MANUAL and is the only remaining human action.

## 1. Environments

| Environment | What it is | Who touches it |
|---|---|---|
| local | the developer workstation | the operator and the agent |
| staging | a clean directory containing only an extracted release tarball | EP-009 drill, automated |
| production | the player's machine | nobody but the player |

There is no server, no cluster, and no cloud account anywhere in this list.

## 2. Deployment architecture

A player downloads one tarball, extracts it, and runs one binary. That binary reads
content.pack from beside itself, writes saves and logs under the platform data directory,
and opens no socket. There is nothing else.

## 3. Build artifact definition

For each of the three targets:

    monte-cristo-<version>-<target-triple>.tar.gz
      monte-cristo(.exe)          the mc_shell binary, release profile, stripped
      content.pack                the baked content-addressed pack
      content.pack.blake3         its digest
      LICENSE
      THIRD-PARTY-LICENSES.txt    generated by cargo-deny
      README.txt                  install, uninstall, data directory locations

Targets: `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-gnu`, `aarch64-apple-darwin`.

Plus one manifest for the set:

    SHA256SUMS                    one line per tarball

All of it staged into `$MC_ARTIFACT_DIR`.

## 4. Release flow

1. EP-009 M1: version bump and changelog, per RELEASE.md.
2. EP-009 M2: `sh scripts/build.sh --release --all-targets` produces the three binaries.
3. EP-009 M3: bake content, stage tarballs, generate SHA256SUMS.
4. EP-009 M4: the cross-platform determinism drill -- extract each tarball into a clean
   temporary directory and replay `tapes/golden-full.tape` against the shipped binary,
   asserting the hash recorded on Linux. A mismatch on any target fails the node.
5. EP-009 M5: the rollback drill, actually performed (see ROLLBACK.md).
6. EP-010: the full ship gate.
7. MANUAL: publish.

## 5. Exact deploy steps

Everything up to publication is automated:

    sh scripts/build.sh
    cargo run --locked -p mc_tools -- bake --input "$MC_CONTENT_DIR" --output content.pack
    sh scripts/production-readiness-check.sh      # must print: production readiness: ok
    git tag -a "v$(cat VERSION)" -m "MONTE CRISTO v$(cat VERSION)"

**MANUAL step (the only human action; the agent prints this and stops):**

    rsync -av --checksum "$MC_ARTIFACT_DIR"/ /srv/releases/monte-cristo/"$(cat VERSION)"/

The agent must not execute this command. It prints it, states that Auto-Deploy Authorization
is `no`, and appends RUN_COMPLETE.

## 6. Migration steps

There is no database. The only migration concept is the save schema, and it runs on the
player's machine at load time, automatically, per SECURITY.md section 11. Before a release
that bumps the save schema version, EP-009 M3 runs:

    cargo run --locked -p mc_tools -- save-migrate --dir tests/fixtures/saves-v1 --dry-run

and asserts every fixture save from every previously shipped schema version migrates
cleanly. A release that cannot load the previous version's saves does not ship.

## 7. Rollback steps

See ROLLBACK.md. Summary: republish the previous version's directory, which is retained.
Because saves are forward-refusing (INV-13), a player who has already saved under a newer
schema cannot be rolled back silently -- they are told, which is why the schema version is
in the save and checked before interpretation.

## 8. Post-deploy smoke

Against the published artifact, from a clean directory:

    curl -fsSL <published-url>/SHA256SUMS -o SHA256SUMS
    sha256sum -c SHA256SUMS
    tar xzf monte-cristo-<version>-x86_64-unknown-linux-gnu.tar.gz
    ./monte-cristo --version
    MC_HEADLESS=1 ./monte-cristo --replay tapes/golden-smoke.tape --assert-hash

## 9. Deployment STOP conditions

Stop and report if: any target's golden-tape hash differs from the Linux hash; SHA256SUMS
does not verify; a previously shipped save fixture fails to migrate; THIRD-PARTY-LICENSES.txt
is missing or contains a licence outside the allowlist; or the version tag already exists.

## 10. Production verification commands

    ./monte-cristo --version
    ./monte-cristo --verify-content        # digest check against content.pack.blake3
    MC_HEADLESS=1 ./monte-cristo --replay tapes/golden-smoke.tape --assert-hash
